## この演習について

ここまでの演習は「仕様を渡されて、自分で書く」形式だった。でも実際の開発では、**すでに書かれたコード(自分やチームメイト、あるいはAIが書いたコード)を読んで、問題を見つける**という別の力が必要になる。

以下の3つのコード例には、それぞれ問題が1つずつ潜んでいる。**何が問題か、1章で学んだ内容をもとに指摘し、修正したコードを書いてください。**

問題の数はヒントとして書いてあるけど、実際の開発では「何個問題があるか」なんて教えてもらえないことがほとんど。今回は練習として数を示しているだけ、ということは意識しておいてほしい。

---

### コード例1

```ts
interface Order {
  customerName: string
  isCompleted: boolean
}

const completeOrder = (order: Order): Order => {
  order.isCompleted = true
  return order
}
```

**ヒント**:1-02(分割代入・スプレッド構文)、1-08(関数の型)で学んだ内容に関係がある。

<details>
<summary>解答を見る</summary>

**問題**:`order.isCompleted = true`で、**引数として渡された元のオブジェクトを直接書き換えてしまっている**。関数は新しいオブジェクトを返しているように見えて、実は呼び出し元のオブジェクトそのものを変更(ミューテーション)している。Reactでは「既存の状態を直接書き換えない」のが大原則なので、これは見た目以上に危険な副作用を生む。

**修正例**:

```ts
const completeOrder = (order: Order): Order => {
  return { ...order, isCompleted: true }
}
```

スプレッド構文を使い、元のオブジェクトをコピーしつつ`isCompleted`だけ上書きした、新しいオブジェクトを返すようにする。

</details>

### コード例2

```ts
const getCakePrice = (cake: any): number => {
  return cake.price
}
```

**ヒント**:1-07(基本の型注釈)、1-09(interface)で学んだ内容に関係がある。

<details>
<summary>解答を見る</summary>

**問題**:引数`cake`の型が`any`になっている。`any`は「どんな型でも受け入れる、TypeScriptの型チェックを実質無効化する型」なので、`cake.price`が本当に存在するかどうか、コンパイラは一切チェックしてくれない。例えば`cake.pric`とtypoしても、実行するまでエラーに気づけない。

**修正例**:

```ts
interface Cake {
  price: number
}

const getCakePrice = (cake: Cake): number => {
  return cake.price
}
```

`any`を使わず、必要なプロパティ(この場合は`price`)を持つinterfaceを定義して、それを型として使う。「型が分からないから`any`」は、TypeScriptを使う意味を失わせてしまう典型的なアンチパターン。

</details>

### コード例3

```ts
type CakeKind = "shortcake" | "chocolate"

const getCakeLabel = (kind: CakeKind): string => {
  if (kind === "shortcake") {
    return "ショートケーキ"
  }
}
```

**ヒント**:1-10(union type / リテラル型)で学んだ内容に関係がある。

<details>
<summary>解答を見る</summary>

**問題**:`CakeKind`は`"shortcake" | "chocolate"`の2択のはずなのに、`kind === "shortcake"`の分岐しか書かれていない。`kind`が`"chocolate"`だった場合、関数は何も`return`せず、`undefined`を返してしまう(関数の戻り値の型が`string`なのに、実質`undefined`が返りうる状態)。

**修正例**:

```ts
const getCakeLabel = (kind: CakeKind): string => {
  if (kind === "shortcake") {
    return "ショートケーキ"
  }
  return "チョコケーキ"
}
```

すべての選択肢に対応する分岐を書く。もし選択肢が増えた場合に書き忘れを防ぎたいなら、`switch`文と`never`型を使ったチェック(これは1章補講で扱う発展的な内容)を使う方法もある。

</details>

## まとめ

今回見つけた3つの問題(直接書き換え、`any`での誤魔化し、分岐漏れ)は、**AIが生成するコードでも実際によく見かけるパターン**。「動くから大丈夫」ではなく、「なぜこの書き方が問題なのか」を説明できるようになることが、この演習のゴール。
