## この演習について

ここまでの4章では「正しく動くコードの書き方」を扱ってきたけど、実際の開発では「エラーが起きた時に、どう原因を突き止めるか」の方が、AIに頼らず開発する上でずっと重要になる。このレッスンでは新しい文法は学ばず、「エラーメッセージの読み方」そのものを扱う。

## 説明

エラーメッセージを読む時の基本的な手順:

1. **何のエラーか**(エラーの種類・メッセージ本文を読む)
2. **どこで起きたか**(スタックトレース——エラーが発生した場所の一覧——のうち、自分が書いたファイルの行を探す。ライブラリ内部の行は基本的に無視していい)
3. **なぜ起きるパターンが多いか**(そのエラーの種類には、典型的な原因がいくつかある)

大事な心構え:**エラーメッセージは「敵」ではなく「ヒント」**。特にTypeScriptのエラーは、実行前に「ここが間違ってる可能性がある」と教えてくれる、むしろ親切な仕組み。

## 実際にプロジェクトで遭遇したエラーを読む

前にSupabaseのマイグレーションで実際に遭遇した、2つの本物のエラーを振り返ってみる。

**エラー1**:`infinite recursion detected in policy`

これはPostgreSQLが「このRLSポリシー、自分自身を無限に参照してますよ」と教えてくれてるエラー。原因は、`team_members`テーブルの閲覧ポリシーが、判定のために`team_members`テーブル自身を検索する作りになっていたこと。「無限」「recursion(再帰)」というキーワードから、"何かが自分自身を呼び続けている"と推測できる、という読み方の練習になる実例。

**エラー2**:`permission denied for table exercise_progress`(のような形のエラー)

「権限がない」と教えてくれてるエラー。これはコードのロジックミスではなく、「そもそもそのテーブルへのアクセス権限(GRANT)が設定されていない」というデータベース側の設定不足が原因だった。エラーメッセージに`permission denied`と出たら、コードの中身を疑う前に、アクセス権限の設定を疑う、という判断の練習になる。

どちらも、エラーメッセージの中の単語(`recursion`, `permission denied`)が、原因を特定する直接のヒントになってたというのがポイント。

## よく出会うことになる、他のエラーパターン

今後の開発で高確率で出会う、代表的なエラーもいくつか紹介しておく:

**TypeScriptのコンパイルエラー**:
```
Type 'string' is not assignable to type 'number'.
```
→ 「型が合っていない」という、1章で扱った内容そのもの。どの変数に、どの型を期待してたかをエラーメッセージの前後から読み取る。

**Reactの警告**:
```
Warning: Each child in a list should have a unique "key" prop.
```
→ 2章で扱った`key`の書き忘れ。エラーではなく警告(コンソールに赤ではなく黄色系で出ることが多い)だけど、無視せず直すべきサイン。

**実行時エラー**:
```
Cannot read properties of undefined (reading 'name')
```
→ 「`undefined`に対して`.name`を読もうとした」というエラー。1章のオプショナルチェイニング(`?.`)で防げる典型パターン。「どの変数が`undefined`だったのか」を、エラーメッセージの直前のコードから逆算する練習になる。

## コラム:Java・Railsとの対応

### Java

Javaのスタックトレースは、Next.js/TypeScriptのそれよりも行数が長く、詳細なことが多い(`NullPointerException`など、例外の種類ごとに専用の名前がついてる)。ただ「一番上の、自分が書いたコードの行を探す」という基本の読み方は共通してる。

### Rails

Railsの開発環境では、エラーが起きるとブラウザ上に、該当するコードの該当行がハイライトされた、詳細なエラーページが表示される(有名な"Rails 500エラー画面")。Next.jsの開発サーバーも同様に、ブラウザ上でエラーのオーバーレイを表示してくれる機能があり、考え方は近い。

## 一緒にやってみる

この演習は「エラーメッセージを読む」もの。読む練習をするために、
まず**自分でエラーを起こしてみよう**。演習と同じ種類のエラーが出るコード:

```ts
const formatName = (name: string | null) => name.toUpperCase();

console.log(formatName(null));
```

このコードを、**コピペせずに自分の手で入力してみてほしい**。出てきたメッセージの
「どういう操作が」「何に対して」失敗したのかを、声に出して言えるか試してみよう。

<TryIt />

読み方の型を整理すると:

```
TypeError: Cannot read properties of null (reading 'toUpperCase')
   ^種類        ^何が起きたか                  ^どの操作で
```

- **エラーの種類**(`TypeError`など)で、大まかな原因の系統が分かる
- **`reading 'xxx'`**の部分が、実際に触ろうとしたプロパティ名。ここが手がかりになる
- そのあとに続く行(スタックトレース)は、**上から順に「どこで起きたか」**

演習では、このメッセージを読んで原因と調べる場所を説明することになる。
